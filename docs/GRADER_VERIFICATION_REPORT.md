# Grader verification report

Verification date: October 27, 2026. Detailed evidence can be regenerated with `scripts/verify_grader.py`; the command is provided below. Checks are scripted software validation, not model experiments, independent reviewer execution or clinical validation.

## Results

The benchmark suite contains 89 passing tests. The fixture suite accepted 20 reference paths and 12 alternatives and rejected 60 negative fixtures (20 unchanged states, 20 inconsistent final states and 20 repaired forbidden histories). Eight additional targeted checks produced the expected outcomes. The verification script regenerates full logs, snapshots and verdicts. All counts describe this source snapshot only.

## Generated evidence paths

Run from the benchmark root:

```bash
python3 scripts/verify_grader.py . ../grader_reproduction
```

Use a new output directory outside the source tree. All evidence paths below are relative to `../grader_reproduction/`, not the repository: `event_and_constraint_map.json`, `targeted_results.json`, `trusted_fixtures/`, and the `RR_006_.../evidence.json` files are generated by this command. They are not bundled inputs.

Final-state consistency is a separate check in Grader.consistency: fixed referral identity/policy, record identities, resolving references, attachment patient identity, appointment uniqueness and validity, acceptance, historical completed-appointment evidence, closure and ticket existence. Grader.grade also checks task-specific constraints and required events. These checks cannot be reduced to the history labels alone.

Allowed outcomes require their declared terminal status and every listed predicate. The implemented ordinary predicates are packet_complete, provider_eligible, acceptance_valid, authorization_valid, appointment_valid, no_duplicate_appointment, current_report_matches, all_required_receipts and closure_valid. The escalation predicates are escalation_ticket_valid, human_action_allowed, barrier_true and evidence_supports_barrier. They map to interface §8.3/§8.5, GRADING_SPEC.md and the shared public_policy.escalation_evidence_contract. Each task's public booking/recipient policies and tool observations supply the domain facts. Unknown predicates fail closed.

## Rejected action and executed violation

RR_006_rejected_then_recovered/evidence.json records an AUTHORIZATION_INVALID booking rejection followed by successful recovery. The rejected operation changes no domain state and the final verdict passes with no hard violations.

RR_006_synthetic_executed_bad_booking/evidence.json starts from a successful trace and deliberately changes the booking's pre-operation authorization status to denied while retaining its valid final state. The grader rejects it with authorization_record_tampering and booking_without_valid_prerequisites. This is a synthetic grader-input fixture, not an action executable through the safe public tools. It does not isolate a single violation category. Both the original and modified verdicts are preserved.

The other negative fixtures in trusted_fixtures deliberately inject forbidden intent changes and repairs. They test history-sensitive rejection, not real agent behavior. Existing tests also cover rejected operations coinciding with environment events: an external state change is distinguished from an agent operation's mutation interval.

The event-isolation checks modify exported grader inputs and are not publicly executable paths. For RR_019/RR_020, required_event_ids also controls the evidence freshness threshold. Removing that field is therefore not a pure removal of an outcome gate. The unchanged-source event tests confirm that RR_016/RR_018 fire once, survive reopen, and reject incomplete recovery. Direct-booking fixtures use authored IDs and are not agent baselines.

## Verification scope

These checks verify the tested paths and fixtures, not exhaustive coverage of every possible action history. They do not establish independent human execution, clinical validation or empirical difficulty calibration.

The verification script exports trusted logs, fixtures, verdicts to a separate output directory. Recorded historical results are not a claim that every possible trajectory has been verified.

## Reproduction

From the benchmark root run `python3 -m unittest discover -s tests -v`. From the benchmark root run `python3 scripts/verify_grader.py /absolute/path/to/benchmark /absolute/path/to/new-evidence-directory`. Evidence must be outside the benchmark source tree. Keep trusted traces and hidden task details on the evaluator side, away from scored agents and blind reviewers until their initial judgments are saved.
